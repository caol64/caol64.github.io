[创造球会04游乐场](https://saka04.babyno.top/)上线了一个新功能：显示球员头像。这篇文章聊聊它背后的技术细节。

![](imgs/posts/2026-10-30-sakatsuku-04-player-face-system-analysis/1.webp)

球会系列从 3 代起就迈入了全面 3D 时代，球员形象和立绘全部由模型加纹理实时渲染，前作里那种预设照片再也没出现过。

借助 Ghidra 和 AI，我把世嘉当年的 3D 渲染引擎还原了出来，如今它能在现代显卡上照常跑起来。

## 球员脸部系统

《球会04》的数据文件里存放着一个庞大的角色数据库：**15,034** 条面部外观记录，涵盖球员、教练与球探，每条记录大小精确到 **64 字节**。

顺着世嘉的代码往下捋，可以发现这条脸部资产管线一开始就分了两条岔路：

```
                    ┌─ [team_id > 1] ──► J联赛真实球员 ──► 专属贴图索引 (jfacetex.bin)
64-Byte 球员记录 ──┤
                    └─ [team_id <= 1] ─► 海外/架空球员 ──► 动态图层烘焙 (13图层拼接)
```

* **真实球员**：一人一张专属贴图，相当于预先拍好的证件照。
* **海外及架空球员**：为上万人单独画一遍贴图不现实，于是世嘉改用一套**动态图层烘焙机制**——读取 64 字节记录里的肤色、眼型、眉形、胡须、法令纹等参数，从基础图集中把对应零件裁出来，现场拼成一张 128×128 的“脸皮”（直接贴在模型上的脸部贴图）。

## 从二进制到 3D 网格变形

原版程序里的人脸模型由一套相当严密的变形系统驱动，大体分三步走。

### 1. 基础网格解析（HSB / MDB 格式）

特写级的高模脸皮存放在 `kao.hsb` 中，头发模型则存放在 `hairmdl1.bin`（MDB 格式）。

### 2. 43 维局部滑条与稀疏差值流（Morph Shape Keys）

每条球员记录从第 21 字节开始，存了 43 个有符号字节（`int8`），每一个就是一根面部微调滑条：调眼窝深浅、调颧骨高度、调下颌宽窄，各管各的。

所有滑条叠加完之后，程序还会再强行叠上一段硬编码的**全局基准校准流**，权重固定为 `0x42 (66)`，把骨架拉回世嘉设计的那张标准脸，完整的 3D 头像轮廓才算定形。

### 3. 纹理解析（BMR 格式）

2D 纹理字典和 UV 图集切割规则都装在 BMR 格式的容器里。

## 材质烘焙与发型处理

### 1. 架空球员的 13 图层绝对定位烘焙

架空球员的贴图并不存在文件里，而是每次在内存中现拼。拆到图元布局表就能看清，128×128 的画布被切成了两半：

* **左侧 3/4（96px 宽）**：脸部主体，依次叠上底膜脸皮、眼眶眼白、眼型轮廓、法令纹、眉毛、鼻梁鼻翼、嘴唇、胡须。
* **右侧 1/4（32px 宽）**：一条独立保留列，专放眼球（16×16）、上下牙齿（16×16），以及下颌和口腔的立体阴影。

真实球员则省去这一步，贴图早就存好了：

![](imgs/posts/2026-10-30-sakatsuku-04-player-face-system-analysis/entry_0_0.png)

### 2. 发型透贴与 Alpha 阈值

PS2 的 GS（Graphics Synthesizer）自带一套 Alpha 测试硬件。程序里有一张专门的 `AREF` 阈值表：每种发型渲染时，纹理 Alpha 通道低于阈值的像素会被直接丢弃（Alpha Cutoff），发丝缝隙里才能透出后面的皮肤。

## 离屏渲染管线

到这一步，内存里已经躺着完整的 3D 网格、法线、材质和发型了。很自然的想法是：**为什么不直接打包成 glTF 丢给前端，让 Three.js / Babylon.js 实时渲染呢？**

考虑再三，前端实时 3D 的方案还是被否掉了，原因其实很现实：

1. **尺寸与交互需求严重不匹配**：头像展示框通常只有 **128×128 像素**，本质就是一张帮玩家认人的名片缩略图。为了邮票大小的图，拉进一整套 WebGL 运行时、轨道控制器（OrbitControls）和一堆着色器，典型的杀鸡用牛刀。
2. **确定性与极致轻量**：离线预先烘焙成 2D 静态图，前端就只剩最纯粹的图片渲染，还能直接吃浏览器原生缓存。

所以工程上的最优解很清楚：**在后台批量离屏出图**。部署环境多半是没有显示器的无头服务器（Headless），于是选了基于 EGL / CGL 的现代 Python 无头 OpenGL 库 **ModernGL**。

### 1. 动态自适应“摄影棚”相机

要让 15,034 张头像的构图保持一致，相机坐标不能写死，得按每个网格的包围盒实时算出 MVP 矩阵：

```python
# 计算包围球与视锥距离
radius = max(float(np.linalg.norm(maximum - target)), 0.01)
distance = radius / (math.sin(vertical_fov / 2.0) * 1.2) / zoom
# 经典 45° 视场角与固定机位朝向
eye = target + direction * distance
```

### 2. 着色器实现

整条管线相当克制：

* **顶点着色器**：只做 MVP 空间变换，把 UV 和法线传给下游。
* **片元着色器**：算一遍简单的半兰伯特漫反射，再按 Alpha Discard 精准剔除头发和透明五官的边界；结果写进开了 4x MSAA 抗锯齿的 Framebuffer，Blit 到解析缓冲（Resolve Framebuffer），最后压成 WebP 字节流。

## 专为 Web 端设计的紧凑归档格式

一万多张 WebP 渲染完，怎么送到前端？如果老老实实存成 15,000 个小文件，会同时引爆两个问题：

1. **本地文件系统灾难**：满屏的几 KB 小文件把 Inode 挤爆，打包、解压、传输全都慢得离谱；
2. **HTTP 性能灾难**：前端轮流请求几万张小图，光是连接握手就是一笔巨债。

为此我设计了一套定制的轻量紧凑归档格式 **`FAVI`（Fast Avatar Index）**：

```
avatars/
 ├── index.bin              <-- 固定尺寸头部 + 每人8字节的查找表
 ├── avatars-000.pack       <-- 2MB 分片二进制包
 ├── avatars-001.pack
 └── ...
```

* **定长索引表（`index.bin`）**：结构是 `Header (64B) + Entry (8B * N)`，每个条目只占 8 字节。
* **分片存储（`avatars-xxx.pack`）**：每个分片控制在 **2MB** 左右。前端先下载一份只有几十 KB 的 `index.bin`，之后既能算出偏移量、用 **HTTP Range Request** 按需切出单张 WebP，也能在客户端按分片整包预缓存，CDN 的请求压力就此摊平。

## 已知问题

- 左右手坐标系没做转换，目前头像与游戏中呈现左右镜像
- 球员脸型偏长、偏尖
- 光源位置或法线计算有误，部分球员的脸偏暗

## 结语

从 Ghidra 里扒机器码还原算法公式、复刻 PS2 的浮点特性，到用 ModernGL 离屏着色、自造 FAVI 紧凑格式，这条管线几分钟就能把 15,034 名球会角色全部跑完，输出高质量 WebP。

二十年前绿茵场上的那些熟悉面孔，如今在现代 Web 技术栈下重新有了模样。欢迎移步[创造球会04游乐场](https://saka04.babyno.top/)看看效果。
