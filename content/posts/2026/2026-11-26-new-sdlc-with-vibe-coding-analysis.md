> **原文**：*The New SDLC With Vibe Coding — From ad-hoc prompting to Agentic Engineering*
> **作者**：Addy Osmani、Shubham Saboo、Sokratis Kartakis（Google）
> **发布**：2026 年 5 月，共 51 页；属于 Google Agents 系列课程白皮书

AI 写代码已经够快了，快到你开始怀疑自己在这个流程里还剩下什么。

Google 这篇白皮书想说的就一句话：**瓶颈已经从“写出来”挪到了“说清楚要什么、以及确认它真的对”。** 下面是我读完之后的整理，只保留能直接上手复用的部分。

> 如果你读过我之前写的[《Vibe Coding 时代的“认知破产”》](https://babyno.top/posts/2026/05/cognitive-bankruptcy-in-the-era-of-vibe-coding/)，可以把这篇当成它的下半场：上一篇讲的是“为什么全盘交给 AI 会让你丢失理解”，这一篇讲的是“怎样给 AI 套上约束，让它替你干活、而你仍然掌握全局”。

## 一、先分清你站在光谱的哪一端

Vibe Coding 是 Karpathy 在 2025 年 2 月提出的：跟着感觉走，接受 AI 的输出，不读代码，报错就贴回去。2026 年初，他又补了个词——**Agentic Engineering**，指光谱上更严谨的那一端。

一端是随手，一端是严谨，中间没有好坏，只有**风险和成本**的取舍。

![Vibe Coding 到 Agentic Engineering 的光谱](imgs/posts/2026-11-26-new-sdlc-with-vibe-coding-analysis/vibe-coding-spectrum.svg)

### 区分线只有一条：验证

- **测试（Tests）**验证**确定性**的部分：给定输入，得到预期输出，由代码检查。
- **评估（Evals）**验证**非确定性**的部分：Agent 走对路了吗？工具选对了吗？结果达标了吗？靠标注数据集、评分标准（Rubric）和模型评审来判断。

**两者缺一，提示词写得再精巧，做的仍然只是 Vibe Coding。**

> 团队不必争论“我们算不算 Vibe Coding”，只查两件事：有没有自动化测试？有没有带 Rubric 的 Eval？两个都有，才算工程化。

### 这条线画在哪，取决于风险

- 周末原型、一次性脚本：放心纯 Vibe，越轻越好。
- 支付、权限、数据处理这类生产代码：必须走严谨那一端。
- 大多数工作落在中间：**真正稀缺的能力是判断每个任务的线该画在哪里**，而不是选边站。

## 二、上下文工程：把话说到 AI 能用的程度

> 代码质量更多取决于**上下文质量**，而不是提示词技巧。

换个问法就通了：别想“怎么骗 AI 写得好一点”，想想**“一个新同事要能干好这活，需要知道什么？”** 把这些写成 AI 能读的形式，就是上下文工程。

上下文分两层，这是唯一需要记住的权衡：

- **静态上下文**：每条请求都带着。规则文件（AGENTS.md / CLAUDE.md）、全局记忆、人设。放太多是烧钱又稀释信号，放太少 Agent 会忘掉硬规则。
- **动态上下文**：按需加载。Skill 指令、工具结果、检索到的文档。只在用到时才付 token。

**Agent Skills** 是动态上下文里最实用的模式，靠的是**渐进式披露**：启动时 Agent 只看到一行描述，任务匹配上才加载完整指令，真需要时才翻深层资料。结果就是——可以挂几十种专业能力，只为正在用的那种付钱。

## 三、新 SDLC：压缩只发生在实现阶段

AI 带来的不是“更快的旧流程”，而是**压得不均匀的新流程**：实现从几周压到几小时，而需求、架构、验证仍然得按人的节奏走。

![AI 对 SDLC 各阶段的压缩程度](imgs/posts/2026-11-26-new-sdlc-with-vibe-coding-analysis/sdlc-compression.svg)

| 阶段 | AI 做什么 | 你该做什么 |
| --- | --- | --- |
| 需求与规划 | 生成用户故事、找你容易漏掉的边界情况、从自然语言生成 API Schema | 定义意图，判断取舍 |
| 设计与架构 | 架构定了之后就搭脚手架、跨模块生成一致的范式 | **做出并记录**结构性决策 |
| 实现 | 整个功能、复杂算法、多文件协同修改 | 从“写”转向“审、引导、验证” |
| 测试与 QA | 生成边界用例、性质测试 | 设计 Eval 套件，定义什么叫“正确” |
| 评审与部署 | 首轮评审（Bug、风格、安全、性能）、健康监控、自动回滚 | 判断设计、可维护性和战略一致性 |
| 维护与演进 | 读懂遗留代码、迁移框架、更新废弃 API | 确认重构安全 |

注意两件事：

- **最危险的不是报错** 一个流畅的输出如果跳过了验证步骤，比明显报错更危险。所以除了看结果，还要看**过程**：工具调用走对了吗？中间推理链有没有偷懒？
- **最被低估的机会** 维护与演进。以前“太危险不敢碰”的老代码，现在可以放心重构——这可能是 AI 给存量项目带来的最大红利。

原文还提醒：这套阶段划分反映的是 2026 年中的状态，12 个月后边界可能完全不同。**会变的只有工具，不变的判断力、品味和验证能力。**

## 四、Agent = 模型 + Harness

开发者该产出的东西变了：不是代码，而是一条**能稳定产出代码的流水线**——规格、Agent、测试门禁、反馈回路、护栏。

![Agent = Model + Harness](imgs/posts/2026-11-26-new-sdlc-with-vibe-coding-analysis/agent-model-harness.svg)

模型只是车间里那台裸发动机，光有它造不出车。皮带、齿轮、传感器、流水线这一整套，才是 Harness：

- **指令与规则文件**：AGENTS.md、CLAUDE.md、Skill，定义“它是谁、在乎什么、禁止做什么”
- **工具**：函数、MCP 服务器，**以及告诉模型何时怎么用的那段说明文字**
- **沙箱与执行环境**：代码在哪跑，能碰什么，不能碰什么
- **编排逻辑**：子代理派生、模型路由、专家交接
- **护栏与 Hooks**：在工具调用前、文件编辑后、提交前跑的确定性代码，专治“Agent 不该忘但老忘”
- **可观测性**：日志、追踪、成本与延迟，没有它你根本不知道 Agent 在正常干活还是在悄悄漂移

> **这是团队自己的表面积，不是模型厂商的。**

原文里最有冲击力的一句是：同一个 Agent，既能拿来 Vibe Coding，也能做 Agentic Engineering，区别只在 Harness 配得多细；而**大多数 Agent 失败，复盘下来都是配置失败**——缺工具、规则含糊、没护栏，或者上下文塞满了噪声。

这不是空话：

- **Terminal Bench 2.0**：不换模型，只改 Harness，同一个编码 Agent 从 Top 30 之外杀进 **Top 5**。
- **LangChain**：模型固定，只调系统提示词、工具和中间件，分数 **+13.7**。

所以“等下一代模型”往往是一笔错的投资。模型是外部变量，Harness 才是能自己攒的资产；新模型发布时，Harness 好的团队立刻受益，Harness 差的团队受益有限。

## 五、你的角色：从指挥家到编排者

| | 指挥家 | 编排者 |
| --- | --- | --- |
| 节奏 | 实时、手把手，盯着代码出现 | 异步，多 Agent 并行委派 |
| 适合 | 复杂逻辑、棘手 Bug、陌生代码库 | 定义清晰的修复、迁移、测试生成 |
| 风险 | 你自己就是瓶颈 | 规格和验证跟不上，产出就失控 |

两种都得会，但值得练的是编排者那四项：**规格化、分解、评估、系统设计**。

### 为什么总差最后 20%

AI 能一口气写出功能约 80% 的代码，剩下 20%——边界情况、错误处理、集成点、细微的正确性——极度依赖上下文知识，恰恰是当前模型最缺的。

更麻烦的是，错误形态也变了：从语法错误变成**概念性失败**，比如对业务逻辑的错误假设、遇到模糊需求不澄清、漏掉边界、架构上埋雷。这些代码“看起来是对的”，甚至能通过基础测试。

> 把 AI 当手快的实习生，而你是审核者：它做规格清楚、量大的事，你盯模糊需求、架构权衡、正确性验证。

## 六、工具怎么选：按任务，不按“自主性”

- **编辑器**：保持心流、随手改（Copilot、Cursor、JetBrains AI）
- **终端**：多文件改造、探索陌生代码库（Claude Code、Codex CLI、Cline）
- **后台**：一句话说得清、扔出去就不管的任务，比如修已知 Bug、批量补测试、框架迁移（Jules、各类后台 Agent）

别按“哪个更自主”来排座次，**按任务选入口**。同一个人一天里三种都会用。

### 当你要造的东西本身就是 Agent

一次性脚本或个人自动化：普通编码 Agent 就够了。面向真实用户的规模化服务，它就是**产品**，得有持久记忆、权限隔离、能拦住回归的 Eval、可追踪的可观测性。多 Agent 协作也别自己发明轮子：工具访问用 **MCP**，跨 Agent 委派用 **A2A**。

Anthropic 2026 年初有个标志性实验：Agent 团队两周内用 Rust 写出一个可运行的 C 编译器，人只定方向和审结果。瓶颈确实从“写代码”挪到了“定义它该做什么”和“验证它做到了没有”。

## 七、算一笔账：免费的都是最贵的

![累计总拥有成本示意](imgs/posts/2026-11-26-new-sdlc-with-vibe-coding-analysis/tco-curve.svg)

- **CapEx**：前期投入。Vibe 几乎为零，Agentic 很高——要设计 Schema、写测试、最重要的是搭上下文。
- **OpEx**：持续成本。Vibe 很高，而且**会滚雪球**。

Vibe 的 OpEx 从三个地方漏出来：

1. **Token**：把整个仓库塞进上下文，反复让模型修自己没验证过的错，一次通过率极低。
2. **维护税**：半年后出 Bug，得花几天逆向理解 AI 写的“意大利面”。
3. **安全返工**：没有评估 Harness，代码生成得越快，漏洞也来得越快。生产环境修漏洞比设计阶段贵几个数量级。

省钱的办法也就三个：**上下文工程**（高信号，提高一次通过率）、**动态上下文与 Skills**（只为用到的能力付费）、**模型路由**（难的交给大模型，测试生成、代码评审、CI 监控交给小模型或本地模型）。

> 这套说法能让你跟老板解释“为什么先搭脚手架再上量”，但原文全是定性论证，没有定量数据——真要立项，数字得你自己补。

## 八、落地清单

按角色挑，不贪多。

### 个人

1. **建一个 AGENTS.md，从 10 行开始**：技术栈、约定、硬规则、工作流。Agent 每犯一次不该再犯的错，就加一条。
2. **挑一个重复性工作流，做成你第一个 Agent**：研究、代码评审、周报。亲手做完一个端到端，胜过读一百篇文章。
3. **先写测试和 Eval，再生成代码**——它们是你和 AI 之间最精确的契约。
4. **要上线的每一行都得审**：对“看起来很聪明”的代码保持怀疑，尤其**检查 import 的包是否真实存在**。
5. **别丢基本功**：调试、系统设计、对正确性的直觉。AI 放大你的专业能力，不替代它。

### 团队负责人

1. **把上下文工程当一级工程实践**：AGENTS.md、提示词、Eval 套件、Skill 库按代码对待——走 PR 评审、跟着版本走、有人负责。
2. **门槛设在 Eval，而不是 Demo**：Demo 证明能成功一次，Eval 证明能稳定成功。
3. **审查强度不低于人写的代码**，重点关注幻觉依赖、错误处理缺口、细微的正确性偏差。
4. **原型和生产分开**：分仓库、分分支、分环境。边界模糊的团队，迟早让原型意外上线。
5. **Harness 是团队资产**：提示词、Skill、MCP 连接、评估脚本，都按基础设施管理。

### 组织

1. **把 AI 辅助开发当工程投资，不是“提效功能”**：只发工具不配套，得到的是速度和技术债一起涨。
2. **先建生产底座再上量**：CI 里跑 Eval，追踪每次 Agent 运行，权限隔离，安全评审盯着生成代码的典型失败。
3. **用开放标准留后路**：MCP + A2A，别把自己焊死在一家平台上。
4. **为人和 Agent 的混合团队做规划**：评审、On-call、团队结构都得跟着改。
5. **招聘和培养围绕判断力**：未来最值钱的工程师，是**最会指挥 Agent 的人**，不是敲代码最多的人。

### 三阶段路线（6 个月跑完）

| 阶段 | 时间 | 关键动作 | 看什么指标 |
| --- | --- | --- | --- |
| 起步：建立 Harness 基线 | 0–1 月 | 每个仓库写 10 行 AGENTS.md；统一编码 Agent 工具；定原型/生产边界 | AGENTS.md 覆盖率；PR 一次通过率 |
| 加固：验证体系 | 1–3 月 | 测试先行；建带 Rubric 的 Eval；评审清单加 AI 专项；提交前 Hook 查密钥和依赖 | Eval 覆盖率；AI 代码引入的线上缺陷率 |
| 规模化：工厂化 | 3–6 月 | Skill 库和 MCP 连接变成平台资产；后台 Agent 做迁移和补测试；模型路由；全链路可观测 | 单功能交付周期；每个 PR 的 token 成本；评审者负载 |

### 五个可以直接借用的判断

1. **Agent 效果不好，先审 Harness，再决定换不换模型**：规则含糊？工具缺失？上下文噪声太大？没有 Hook？
2. **“有没有 Eval”就是上线硬门槛**，和单测覆盖率并排写进检查清单。
3. **AGENTS.md 是新的新人入职手册**，同时服务 AI 和新同事，回报率最高。
4. **原型和生产分开**，防止 vibe 出来的东西意外上线。
5. **模型路由直接省钱**，大模型做架构和复杂实现，小模型做测试生成、评审和 CI 监控。

### 三个必须警惕的误区

- ❌ **上了 AI 工具就等于提效**：没有 Harness 和 Eval，速度和技术债一起涨。
- ❌ **Demo 跑通就能上线**：Demo 只证明能成功一次。
- ❌ **以后不用培养写代码的能力**：基本功生疏了，你连 AI 写的代码都审不动。

## 九、最后，请记住三句话

1. **结构能规模化，氛围感不行。**（Structure scales, vibes don't.）所以 AGENTS.md、Eval 套件、Hooks 这些看起来“拖慢起步”的东西，才是让一个团队从几个人扩到几十个人还不失控的前提。
2. **AI 放大你的工程文化**，长处和短处一起放大。测试扎实、评审严格的团队会被推得更快；靠混乱运转的团队只会更快地制造混乱。
3. **人的角色在进化，而不是在缩小**。指挥家那部分不会被淘汰，只是那些能说清规格、判断结果好坏的人，会把差距拉得越来越大。

如果只想记住一句：**别再等下一个更强的模型，先把你自己那层 Harness 配好。** 模型每半年换一次，Harness 是团队真正能积累下来的东西。
