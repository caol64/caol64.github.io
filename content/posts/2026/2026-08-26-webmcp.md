WebMCP 可以理解为一种让 **网页主动向 AI Agent 暴露结构化能力（Tools）** 的机制。

## 传统浏览器自动化的困境

AI Agent 操作网页时，通常需要像人类一样与 UI 交互：

```
AI Agent
   ↓
读取 DOM / Accessibility Tree / 截图
   ↓
寻找按钮、输入框
   ↓
模拟点击和输入
   ↓
观察页面变化
```

这种方式高度依赖网页的具体实现。DOM 结构变了、按钮文案改了、布局换了，Agent 就可能失效。

## WebMCP 的核心思路

WebMCP 让**网页主动向 AI Agent 暴露结构化 Tool**：

```
网页
   ↓
注册 Tool
   ↓
浏览器发现
   ↓
Agent 调用
```

网站不再要求 AI：

> 找到搜索框 → 输入关键词 → 点击搜索

而是直接告诉 AI：

```
search_articles({ keyword: string })
```

**AI 调用的是网站的语义能力，而不是网页上的具体 UI。**

## 与 MCP 的本质区别

|  | MCP | WebMCP |
|--|-----|--------|
| 能力发现 | 配置/连接 Server | 访问网页后发现 |
| 是否需要打开网页 | 不需要 | 需要 |
| 生命周期 | 长期存在 | 页面/标签页生命周期 |
| 主要对象 | 后端服务、应用程序 | 当前网页 |
| 适合场景 | 后台任务、服务级能力 | 页面内业务操作、当前 Session |

一句话：**MCP 是服务 API，WebMCP 是网页 API。** 两者不冲突，可以并存。

## 与 Skill 的区别

WebMCP **不负责让 AI 找到网站**。它不解决：

> AI 如何在互联网中找到这个网站？

完整流程仍然是：

```
Agent 搜索 / 导航 / 根据 URL 进入网站
    ↓
发现 WebMCP Tools
    ↓
调用对应 Tool
```

导航和跨站编排是 Agent Skill 的事；理解并操作当前网站才是 WebMCP 的事。

## 它改变了 Skill 的工作模式

传统 Agent Skill 混合了两类知识：

```
业务逻辑（要完成什么任务）
    +
UI 操作细节（哪个按钮、哪个输入框）
```

UI 操作细节是最脆弱的部分。网站改版后，Skill 就失效了。

WebMCP 把这两类知识分离：

- Agent Skill → 跨站工作流 + 导航 + 高层任务编排
- WebMCP → 网站内部业务能力 + 具体操作实现

于是 Skill 从：

```
打开网页 → 抓数据 → 找输入框 → 输入 → 找按钮 → 点击
```

变成：

```
导航到目标网站 → 根据当前页面的 WebMCP Tools 完成任务
```

## 从 UI 自动化到语义调用

- 传统：`find_button("提交") → click()`
- WebMCP：`submit_article(...)`

前者描述**怎么操作**，后者描述**要完成什么**。

网页的 UI 可以随时变化——按钮换位置、React 改成 Svelte、重新布局。但只要 `submit_article()` 的参数 Contract 不变，Agent 的工作流就不需要变化。

**WebMCP 是网页的 Agent API Contract。**

## 核心价值

过去，网站是给人操作的，AI 必须模仿人。

未来，网站同时提供：

```
                 网站能力
               /        \
              /          \
           UI            WebMCP
           ↓               ↓
         人类            AI Agent
```

WebMCP 是一种 **AI Native Web Interface**。

## 总结

传统 Agent Skill 是从网站外部告诉 AI“这个网站应该怎么操作”；WebMCP 则由网站自己告诉 AI“我能做什么”。

它不是替代 Agent，而是把最脆弱的网站操作知识从 Agent 的外部 Prompt 中，重新交还给最了解自身能力的网站本身。
